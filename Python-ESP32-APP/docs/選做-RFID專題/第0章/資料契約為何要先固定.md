# 資訊補充：資料契約為何要先固定

資料會在不同程式或裝置之間移動時，先約好資料的樣子，才能讓每一段都理解同一件事。

!!! info "這是資訊補充"

    本頁只幫助你理解概念，不需要練習、安裝軟體、連接硬體或設定網路。不讀本頁也能完成[第 0 章首頁](index.md)的固定案例檢查。

## 你會學到什麼

- 用日常的表單和包裹標籤理解資料契約的作用。
- 說出資料交換前要先固定哪些基本規則。
- 看出「不知道」和「沒有」為什麼需要用不同方式表示。

## 先把資料契約想成表單

假設幾個人輪流處理一張包裹寄送單。第一個人填寄件資訊，第二個人看地址分貨，第三個人通知收件人。

如果大家一開始沒有約好表單長什麼樣子，就可能發生這些事：

- 有人把收件地址寫在備註欄，分貨的人找不到。
- 有人把日期寫成 `9/18`，另一個人不知道是哪一年或哪個時區。
- 地址看不清楚時，有人把它當成「沒有地址」，繼續寄送。

資料契約（data contract，資料交換規則）就是這份事先約好的表單：有哪些欄位、每一格能填什麼、資料缺少或不合理時要怎麼處理。它不是一個額外的 App 或套件，而是一組所有資料交換參與者都遵守的規則。

## 放到 RFID 專題會是什麼樣子

RFID 專題後續可能讓 ESP32、訊息服務、Python Gateway、LCD 和手機畫面接力處理同一筆狀態。第 0 章先在一個 Python 程式裡用固定字典模擬這段流程，但規則會沿用到後面的資料交換。

```text
讀卡事件 → Gateway 判斷 → 顯示狀態
```

例如，大家先約好事件要有 `event_id`、`device_id`、`occurred_at` 等欄位；讀卡識別值只能使用遮蔽的教學格式。Gateway 收到資料後，才能知道該檢查什麼；畫面也才能知道哪些文字可以安全顯示。

這就像包裹上的追蹤號碼、寄送時間和配送狀態都有固定位置。不是要讓規則變複雜，而是讓下一個接手的人或程式不用猜。

## 先固定的三類規則

| 要先約好的事 | 日常例子 | 第 0 章中的例子 |
| --- | --- | --- |
| 有哪些資料 | 寄送單要有收件人、地址和聯絡方式 | 事件要有 `event_id`、`device_id`、`occurred_at` 等必要欄位 |
| 資料怎麼寫 | 日期統一寫成年月日與時間 | 時間必須含時區；`event_id` 只能用指定格式 |
| 出問題怎麼表示 | 地址看不清楚時標記「待確認」，不假裝已寄出 | 格式錯誤時顯示「資料格式無法使用」；舊資料改為 `unknown` |

## 為什麼「不知道」不能當成「沒有」

想像配送狀態沒有更新。這可能是包裹還沒寄出，也可能是物流系統暫時沒有回應。兩種情況都不能直接說「包裹遺失」。

第 0 章的 `authorized` 也一樣：

- `True` 表示固定教學資料的比對結果是授權模擬。
- `False` 表示固定教學資料的比對結果不是授權模擬。
- `None` 表示目前無法可靠判斷，例如還在等待資料、讀卡失敗或資料已過期。

把不確定的情況清楚標成「未知」，可以避免舊結果或錯誤資料被當成現在的答案。這是資料交換時很重要的誠實做法。

## 重點整理

- 資料契約就像大家共用的表單：先約好欄位、格式和出錯時的處理方式。
- 規則讓不同程式與裝置不用猜資料的意思，較容易發現格式不一致的問題。
- 資料不可靠時，應清楚表示未知或待確認，不應把它當成肯定結果。
