# 延伸選讀：整合專題故障分流

> 對應主線：[整合專題：完成環境看板](08-整合專題.md)

這一頁協助你依症狀找出資料流中第一個需要查看的位置，而不是同時修改多段程式或接線。

## 讀完後你會知道

- 環境看板的硬體、UART、資料檔、圖表與網頁各自負責什麼。
- 從 LCD、JSON、CSV、圖表與 LED 狀態判斷優先查看哪一段。
- 為什麼同一個 COM 埠只能由一個程式使用。

## 先知道這件事

主線整合專題使用 LCD 作為 ESP32 端顯示器；ESP32 讀取 DHT11、更新 LCD 並送出 JSON，Python 再記錄 CSV、建立圖表與更新 Gradio。這是閱讀現象時的順序。

```text
DHT11 → ESP32／LCD → UART JSON → Python → CSV → 圖表 → Gradio
                                  ↑                         │
                                  └────── LED 命令 ──────────┘
```

## 依症狀找第一個位置

| 看到的現象 | 先查看 | 可先得出的判斷 |
| --- | --- | --- |
| LCD 顯示 `DHT read failed` | DHT11 的 VCC、GND、DATA 與 GPIO 4 | LCD 已能顯示文字，問題優先在感測讀值。 |
| LCD 有讀值，但 Python 收不到資料 | 序列監控的 `sensor` JSON、`115200` 與 Python 的 COM 埠 | 感測與 LCD 已工作；接著看 UART。 |
| 網頁更新數值，卻沒有 CSV 或圖表 | Python 的 `append_csv()`、資料夾與 `dataframe_and_chart()` | UART 和讀取流程已取得資料。 |
| LED 有亮滅，網頁卻沒有狀態文字 | ESP32 的 `sendLedStatus()` 與 Python 對 `status` 的處理 | 命令可能已到 ESP32，問題在回覆或接收判讀。 |
| Python 顯示 COM 埠被占用 | Arduino 序列監控或另一支 Python 程式 | 同一個 COM 埠有其他使用者。 |
| 點陣全暗、反相或閃爍 | 第 6 節的極性、列欄紀錄與掃描程式 | 先讓替代顯示器單獨成功，再加入整合功能。 |

## 用成功證據縮小範圍

每個已成功的結果都能排除一部分問題。LCD 顯示正確溫溼度，表示 DHT11、ESP32 與 LCD 的主要流程已通；這時 CSV 沒增加資料，就不必先改 LCD。相反地，Python 已顯示新數值，表示 UART 資料已進入 Python，接著才看 CSV 或圖表輸出。

!!! note "COM 埠的責任"
    Arduino 序列監控與 Python 都需要開啟同一個 COM 埠。整合儀表板運作時，讓 `integrated_dashboard.py` 成為唯一使用者；其他讀取器會讓它無法連線或讀到混亂資料。

## 常見誤解

### 「網頁沒有更新，就要重新接所有硬體」

不一定。若 LCD 已正常顯示讀值，先沿著 UART、Python、CSV 與 Gradio 的順序查看，能保留已確認成功的硬體部分。

### 「LED 有反應，代表感測資料也一定正常」

不是。LED 使用 `led` 命令與 `status` 回覆；感測資料使用 DHT11 讀值與 `sensor` JSON。兩種流程共用 UART，但負責的內容不同。

### 「定時 JSON 就是這次按鈕要求的資料」

不一定。整合程式以 `read_now` 要求資料，並只接受 `source: "request"` 的回覆；定時送出的 `periodic` 資料不會直接寫入這次的 CSV。

## 重點整理

- 依資料流找第一個沒有出現預期結果的位置。
- LCD、UART、CSV／圖表與 Gradio 可以分段判讀。
- LCD 正常不代表 Python、CSV 或網頁一定正常。
- 同一個 COM 埠一次只能由一個程式使用。
