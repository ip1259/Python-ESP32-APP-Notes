# 資訊補充：什麼是系統耦合性？

系統耦合性（coupling）是在說：兩個部分是否綁得很緊，改其中一個時，另一個也必須跟著修改。

這是純資訊補充，不需要安裝工具、接線或執行程式。

## 你會了解什麼

- 用日常情境理解什麼是高耦合與低耦合。
- 看懂裝置程式、後端服務、App 與雲端服務之間為何可能互相綁定。
- 用「更換 App 時，哪些地方要一起改」判斷一個設計的替換彈性。

## 先從日常情境想像

想像一支只能使用原廠專用充電線的設備。若充電線損壞或想換成另一種接頭，設備本身也可能要跟著調整。兩者綁得很緊，這就是高耦合的感覺。

如果設備使用常見的 USB 連接方式，充電線可以更換，但仍遵守相同接頭與供電規則，替換範圍就比較小。這比較接近低耦合。

低耦合不是完全沒有關係，而是先把雙方要遵守的連接方式說清楚，讓其中一邊有機會替換。

## 高耦合與低耦合差在哪裡？

| 情境 | 高耦合的情況 | 低耦合的情況 |
| --- | --- | --- |
| 更換手機 App | 裝置程式直接依賴某一個 App 服務的專用函式庫或指令。 | App 透過後端的 HTTPS API 交換固定格式資料；更換 App 時，裝置程式通常不必一起改。 |
| 更換雲端服務 | 資料格式、裝置程式與服務設定都只適用某一家服務。 | 裝置送出有明確欄位的事件，後端再依需要接到不同服務。 |
| 修改畫面 | 一個按鈕的文字或畫面配置改變，裝置端也要修改。 | App 畫面改動只影響 App；只要 API 的資料格式不變，後端與裝置程式可維持原本工作。 |

你可以用一個簡單問題判斷：**「如果我想換掉這個部分，還有多少其他部分必須跟著改？」**需要一起改的地方越多，耦合通常越高。

## 在 AIoT 專案裡，哪些地方容易綁在一起？

### 硬體函式庫

有些服務會提供裝置專用函式庫，讓你很快連上它的控制台或手機畫面。這在小型練習很方便，但裝置程式會開始使用該服務專有的函式、資料格式和設定。日後若要換服務或改用另一個 App，可能連裝置端程式都得調整。

### 平台協議與可轉用的能力

專用函式庫不只會改變程式中的函式名稱，也可能帶入平台自己定義的通訊協議（裝置與服務交換資料的規則）與資料通道。例如 Blynk Library 的常見流程使用 Blynk Protocol、Virtual Pin（平台使用的非實體資料編號）、Datastream（平台中的資料通道）與 Blynk 函式；另一種做法則直接約定 HTTP 網址與 JSON 欄位，或 MQTT 的 topic 與 payload。這些欄位、格式與意思的約定，也稱為資料契約。

平台封裝能把常見功能做得很快，適合原型與特定產品。HTTP、JSON 與 MQTT 則是許多不同工具都能使用的共通技術。若只熟悉單一平台的函式和畫面設定，未來換到不同公司的平台或技術環境時，可能還要補上協議、資料格式、錯誤處理與權限設計；若也理解共通協議和資料契約，就比較容易判斷哪些經驗可以沿用。

這不表示使用平台函式庫會阻礙職涯，也不表示平台自訂協議一定不好。重點是不要把方便的封裝當成全部：知道封裝底下解決了哪些通訊問題，並保留使用標準協議的能力，能讓學到的內容更容易轉用。

使用標準協議，也不代表整個系統已經和平台解耦。例如 Blynk MQTT API 使用標準 MQTT 傳輸，但 `ds/...`、`downlink/...` topic、Datastream 名稱、裝置 token 與資料型別仍由 Blynk 定義；Device HTTPS API 使用標準 HTTPS，但網址、token 與 Datastream 參數仍連到 Blynk.Cloud。判斷耦合不能只看傳輸協議名稱，也要看資料模型、身分驗證與功能入口由誰定義。

### 資料格式

如果 App、後端與裝置程式都約定好事件有哪些欄位，例如事件代號、狀態與時間，畫面可以改、程式也可以調整，但資料格式要有意識地維持一致。這種約定能讓替換範圍變小。

### 服務入口

若手機只知道某個服務專用的操作方式，換服務時 App 通常也要重做。若手機只呼叫後端提供的 HTTPS API，後端可以在背後處理資料保存或服務連線，App 不必知道所有細節。

## 用資料流來看替換範圍

一個常見的 AIoT 資料流可以分成幾段：

```text
裝置程式 ── 訊息或網路傳輸 ──> 後端服務 ── HTTPS API ──> 手機或網頁介面
```

- 裝置程式負責讀取感測器、控制元件或送出事件。
- 後端服務負責整理資料、保存紀錄與提供介面可讀取的內容。
- 手機 App 或網頁介面負責顯示畫面與送出使用者操作。

因此，日後若把一種 App 工具換成另一種，只要仍呼叫相同的 API，通常不需要為了換畫面工具而更換裝置硬體、修改裝置端的資料傳輸方式，或改用另一套硬體函式庫。

這不代表完全不用修改：新的 App 仍要重新製作畫面、處理登入或權限，並確認 API 資料格式相容。耦合性是在幫助你縮小修改範圍，不是保證永遠不用改程式。

## 高耦合一定不好嗎？

不一定。若目標只是快速做出單一用途的小型練習，直接使用專用函式庫可能很省時間。當你預期未來會更換 App、加入網頁介面，或改用不同服務時，才更值得優先考慮替換彈性。

另外，低耦合也不等於安全。網路連線、資料格式或 API 都仍要另外處理帳密、權限、資料最小化與錯誤情況。

## 重點整理

- 耦合性描述的是元件之間必須一起修改的程度。
- 高耦合可以讓小型原型更快完成，但替換時常要連帶修改更多地方。
- 平台函式庫可以加快原型；同時理解 HTTP、JSON、MQTT 與資料契約，能讓經驗較容易轉用到不同工具。
- 讓 App 經後端 API 交換資料，可以避免 App 的選擇直接綁住裝置程式。
- 低耦合不會自動解決版本、安全或資料格式問題。
