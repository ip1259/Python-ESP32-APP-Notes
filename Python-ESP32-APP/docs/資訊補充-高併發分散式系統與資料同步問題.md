# 資訊補充：高併發、分散式系統與資料同步問題

當很多人同時使用網站，或同一份資料由多台電腦處理時，「資料有沒有跟上」會變成一件需要仔細設計的事。

!!! info "這是資訊補充"

    本頁幫助你認識網站後端常見的問題，不需要練習、安裝套件、執行程式或設定網路。它不是主線課程、RFID 專題或 FastAPI 子頁的前置條件。

## 你會學到什麼

- 用日常例子理解高併發、分散式系統與資料同步。
- 看出同時修改、重複處理和新舊資料交錯時可能發生什麼事。
- 知道日後設計網站後端時，需要先問哪些問題。

## 很多人同時來：高併發

高併發（high concurrency）可以想成熱門活動剛開放報名，很多人同一秒按下「送出」。

平常只有少數人使用時，網站像一個櫃台，一張申請單處理完再拿下一張。人變多時，就像同時有很多人把申請單遞到櫃台：系統需要決定誰先處理、其他人要等多久，以及資料能不能安全地暫時排隊。

高併發不只是「網站變慢」。如果兩個人同時搶最後一個名額，系統還必須確保不會兩邊都看到「報名成功」。

## 不只一個地方處理：分散式系統

分散式系統（distributed system）是指工作和資料分到多台電腦或多個服務處理。

可以把它想成連鎖門市：不同門市各自接待客人，但總部和其他門市也要知道庫存、訂單或會員資料。這樣做可以讓更多人同時被服務；不過，資料從一個地方送到另一個地方需要時間，也可能暫時送不到。

因此，分散式系統常會遇到一個看似奇怪、其實很正常的情況：不同畫面在短時間內看見的資料不完全一樣。

## 資料同步問題長什麼樣子

以下用訂位系統說明幾種常見情況：

| 情況 | 日常畫面 | 後端需要面對的問題 |
| --- | --- | --- |
| 同時修改 | 兩人同時選到最後一個座位 | 哪一筆結果有效？另一人要看到什麼？ |
| 資料晚到 | 門市已取消訂位，總部畫面晚幾秒才更新 | 暫時看到舊資料時，能不能繼續讓人下單？ |
| 重複送達 | 網路卡住後，按鈕被重按兩次 | 同一筆訂位會不會被建立兩次？ |
| 順序顛倒 | 先收到「取消」，晚一點才收到更早的「建立」通知 | 怎麼分辨哪一筆才是較新的狀態？ |
| 部分失聯 | 某間門市暫時沒有網路 | 它應該停止接單、暫存資料，還是顯示待確認？ |

這些情況不一定表示系統壞了，而是多個地方交換資料時必須先決定的規則。

## 為什麼不能只說「同步就好」

「同步」聽起來像所有畫面立刻完全一致，但真實網路有延遲、斷線和重送。系統通常要在幾件事之間做選擇：

- 希望每個人立刻看到最新資料，還是寧可等待確認？
- 網路不穩時，是暫時不能操作，還是先保存待送資料？
- 同一件事收到兩次時，要怎麼認出它是重複資料？
- 兩筆資料互相衝突時，誰有權決定最後結果？

沒有一個答案適合所有網站。線上購票、聊天室、物流查詢和天氣看板，對「可以晚幾秒」與「絕對不能重複」的要求都不同。

## 從小系統開始理解

本課 RFID 第 3 章的 Gateway 只在一台電腦上執行，並用 `event_id` 關聯事件與回覆、用時間判斷資料是否過期。這些做法能幫助一個小型資料流避免把舊資料當成新資料，但不等於已解決高併發或分散式系統的所有問題。

若日後系統需要讓大量使用者同時存取，或由多台服務共同處理資料，還需要評估資料儲存方式、權限、錯誤處理、監控、備份和實際使用情境。這些屬於網站後端與系統設計的進階範圍。

## 重點整理

- 高併發是很多工作同時進來；重點不只速度，也包括結果是否正確。
- 分散式系統把工作交給多個地方處理，因此資料可能晚到、重複或暫時不一致。
- 資料同步需要先決定重複、衝突、順序和斷線時的處理規則。
- 小型本機範例能幫助理解資料流，但不能直接當成大型網站的完整設計。
