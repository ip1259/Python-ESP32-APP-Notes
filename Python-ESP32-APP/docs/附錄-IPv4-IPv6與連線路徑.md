# 延伸選讀：IPv4、IPv6 與連線路徑的選擇

同一個網址在不同網路、裝置或程式裡，可能走上不同的連線路徑；這一頁說明如何理解這種差異，而不急著把原因歸給單一設定。

## 你會學到什麼

- 分辨網域名稱、DNS 回覆的候選位址，以及 IPv4／IPv6 各自在連線中的位置。
- 理解同一個服務在不同網路或程式裡，可能出現不同等待時間或結果。
- 知道 RFC 8305 的 Happy Eyeballs 如何降低雙協定環境的等待時間，以及它無法證明什麼。
- 用低風險的比較與紀錄方式保留線索，不任意改動裝置或網路設定。

## 開始前

- 你只要知道網址可用來存取網路服務即可；不需要安裝工具、建立帳號或修改任何設定。
- 本頁是通用的概念與故障判讀延伸選讀，不是主線成果、任何 App 或 API 的必要前置。
- 若連線問題涉及帳號、付款、醫療、設備控制或其他重要資料，先停止反覆嘗試，改用該服務提供的正式支援管道。

## 同一個網址，不一定只有一個可嘗試的位址

平常輸入的 `example.com` 是**網域名稱**，像目的地的名稱；實際建立網路連線時，程式還需要知道可前往的位址。

DNS（Domain Name System，網域名稱系統）負責查詢名稱對應的資料。它可能回覆：

- `A` 紀錄：一個或多個 IPv4 位址。
- `AAAA` 紀錄：一個或多個 IPv6 位址。

IPv4 與 IPv6 都是讓資料能在網路上找到目的地的位址系統。它們不是「快」與「慢」的二選一標籤；實際結果還會受到當時的網路、路由、伺服器端與程式連線策略影響。

同一個名稱收到的多個位址，稱為**候選位址**。用戶端可能需要從中排序、嘗試，再使用已成功建立的那一條連線。

```text
網域名稱
    ↓ 查詢 DNS
候選位址（可能有 IPv4、IPv6，且各自不只一個）
    ↓ 排序與嘗試連線
已建立的連線
    ↓
後續的 HTTPS／HTTP 資料交換
```

這張流程只描述連線前半段。連線建立後，還可能因為憑證、登入狀態、伺服器回應或資料內容而成功或失敗。

## 為什麼不同環境的結果可能不同

即使輸入相同網址，不同環境仍可能取得不同候選位址、選擇不同順序，或走到不同的網路路徑。下表列出一些可能影響結果的位置；它不是用來從單次現象直接找出唯一原因。

| 位置 | 可能的差異 |
| --- | --- |
| DNS 名稱解析 | 回覆的候選位址、快取狀態或查詢時間可能不同。 |
| 網路與路徑 | Wi-Fi、行動網路、公司網路的路由與轉送狀況可能不同。 |
| 用戶端 | 程式使用的網路函式庫、逾時、重試與候選位址策略可能不同。 |
| 伺服器端 | 負載、暫時性故障、憑證與 HTTP 回應都可能影響結果。 |

因此，「程式 A 很快、程式 B 很慢」是一項有用的觀察，但它本身不能證明哪一個程式使用 IPv4 或 IPv6，也不能單獨證明伺服器端、網路或程式的哪一層有問題。

## Happy Eyeballs：讓等待不必綁在單一路徑上

RFC 8305 定義的 Happy Eyeballs Version 2，是一種用戶端連線策略。它的目標是在同時有 IPv4 與 IPv6 候選位址時，避免某一條較慢或失效的路徑讓使用者等太久；它不是檢測工具，也不是所有程式都必定採用的功能。

可以把它白話分成四個主要階段：

1. **非同步查詢名稱。** 用戶端取得 IPv4、IPv6 的候選位址，不必假設其中一種一定先回覆。
2. **安排候選位址。** 依系統的位址選擇資訊排序，再讓不同位址家族有機會被嘗試。RFC 6724 提供預設位址選擇的背景，但不是要求使用者手動設定偏好。
3. **錯開發起連線。** 先開始其中一個候選位址的嘗試；若還沒有成功，稍後再開始下一個，而非長時間只等待單一候選位址。實際間隔與順序會因用戶端實作而異。
4. **保留先成功的連線。** 一旦有一條連線建立完成，用戶端使用它並取消其餘尚未完成的嘗試。

這四個階段是理解用的流程，不代表每個程式都用相同時間、相同順序或完全相同的細節實作。RFC 8305 的原文也特別處理 DNS 回覆先後、位址排序與多個候選位址的情況。[RFC 8305](https://www.rfc-editor.org/rfc/rfc8305.html)與[RFC 6724](https://www.rfc-editor.org/rfc/rfc6724.html)是這裡的主要技術來源。

## 它能協助什麼，不能證明什麼

| 可以合理理解 | 不能只靠這件事下結論 |
| --- | --- |
| 錯開多個候選位址的連線嘗試，可降低某一路徑等待過久的機會。 | 某個特定 App、瀏覽器或系統一定採用 RFC 8305。 |
| 同時有 IPv4／IPv6 候選位址時，選擇與嘗試策略可能影響等待感受。 | 某次延遲一定是 IPv6、IPv4、DNS、限流或伺服器端造成。 |
| 已建立 TCP 連線不代表後續 HTTPS／HTTP 請求一定成功。 | 某服務不支援 IPv6，或改成 IPv4 就是通用解法。 |
| 不同網路或用戶端的比較可提供下一步檢查的線索。 | 單次成功或失敗足以排除其他網路、憑證、登入或資料問題。 |

### 平台案例：IPv6-only 網路仍可能使用 IPv4 服務

有些網路環境本身只提供 IPv6。Apple 的開發者文件以 DNS64／NAT64 為例：DNS64 可為僅有 IPv4 的名稱合成可使用的 IPv6 表示，NAT64 則在網路邊界協助 IPv6 與 IPv4 之間轉譯。這個案例提醒我們，不能把「強制只用 IPv4」當成通用排錯方式；在某些環境裡，它反而可能沒有可用路徑。[Apple：Supporting IPv6 DNS64/NAT64 Networks](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/NetworkingOverview/UnderstandingandPreparingfortheIPv6Transition/UnderstandingandPreparingfortheIPv6Transition.html)

這是特定平台文件提供的實務背景，不表示每個裝置、每個網路都使用相同機制。

## 安全地比較與保留線索

遇到同一服務在不同情況下表現不同時，可以先保留足夠比較的事實，不需改動系統設定：

- 固定同一個服務與同一個動作，只做少量比較，避免重複大量請求影響服務或混入更多變因。
- 記下網路類型、使用的程式、開始與結束時間、約略等待時間、結果及可安全分享的錯誤文字。
- 若另一個已可信且可用的網路可以比較，可把結果並列記錄；不要從一次差異直接判定原因。
- 移除或遮罩帳號、token、完整網址查詢參數、內網位址、裝置識別碼與可能含個資的錯誤內容，再分享紀錄。

!!! warning "何時應停止"
    不需要為了這類比較修改 APN、DNS、VPN、Proxy、路由器或系統位址偏好。若問題必須改動這些設定、安裝不明工具或憑證、等待異常久，或資料含有敏感資訊，請停止這項比較，改用可信網路或正式支援管道。

## 常見誤解

### 「IPv6 一定比 IPv4 慢」

不是。速度與可用性受到許多環節影響；IPv4、IPv6 都可能在特定網路或服務上表現良好，也都可能遇到暫時問題。

### 「瀏覽器很快，代表其他程式的程式碼有錯」

不一定。兩個用戶端可能使用不同的快取、DNS 查詢、候選位址排序、逾時或重試策略。這能指出值得比較的條件，還不能單獨找出程式錯誤。

### 「限制成 IPv4 後成功，就能確認 IPv6 壞了」

不能確認。限制條件可能同時影響名稱解析、路徑、轉譯與重試行為；還需要更多可比較的紀錄，才能縮小範圍。

### 「Happy Eyeballs 保證每個 API 都會成功」

不保證。它主要處理建立連線時多個候選位址的等待問題；權限、TLS 憑證、HTTP 狀態碼、伺服器負載與回傳資料仍可能讓請求失敗。

## 理解確認

- 你能分辨網域名稱不是唯一的實際連線位址，DNS 可能回覆多個 IPv4／IPv6 候選位址。
- 你知道 Happy Eyeballs 會安排並錯開候選位址的嘗試，成功後使用其中一條連線。
- 你能把「某環境較慢」記為觀察，而不直接寫成某個 IP 版本或程式一定有問題。
- 你知道改動 APN、VPN、Proxy 或系統網路偏好不屬於這頁的通用處理方式。

## 重點整理

- IPv4 與 IPv6 都可能出現在同一個網域名稱的候選位址中。
- DNS 回覆、網路路徑、用戶端策略與伺服器端狀態，都可能使不同環境看到不同結果。
- RFC 8305 的 Happy Eyeballs 用排序與錯開嘗試減少等待；它不是任何特定程式的實作證明。
- 先記錄可觀察事實並保護敏感資訊，比直接修改網路設定更安全。
