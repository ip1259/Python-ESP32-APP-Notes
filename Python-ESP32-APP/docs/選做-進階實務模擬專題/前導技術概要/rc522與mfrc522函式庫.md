# RC522 與 MFRC522 函式庫

RC522 是近距離感應卡讀取模組；`MFRC522` 函式庫則把 ESP32 與模組之間的通訊整理成較容易使用的函式。

## 你會學到什麼

- 理解 ESP32、SPI、RC522 與 `MFRC522` 函式庫各自負責什麼。
- 看懂初始化、偵測卡片、讀取成功與結束通訊的基本順序。
- 分辨「讀到卡片」與「確認使用者可以通過」是兩件不同的事。

## 開始前

- 本頁是概念與函式庫介紹，不需要接線或執行程式。
- 建議先閱讀[SPI 通訊與多裝置](spi通訊與多裝置.md)，了解 RC522 使用的 `SCK`、`MOSI`、`MISO` 與 `SS`／`CS` 線路角色。
- 後續實作只使用明確獲得允許的練習卡，不使用悠遊卡、信用卡、學生證、公司或社區門禁卡。
- RC522 使用 `3.3V`。實際接線前必須先拔除 ESP32 的 USB，並以對應章節重新確認腳位與模組規格。

## 四個角色怎麼合作

| 角色 | 白話用途 | 不負責什麼 |
| --- | --- | --- |
| ESP32 | 執行程式，決定何時請 RC522 檢查附近的卡片。 | 不會因為讀到卡片就自動知道使用者身分。 |
| SPI | 提供 ESP32 與 RC522 交換資料的線路與共同節拍。 | 不判斷卡片是否在名單中。 |
| RC522 | 與附近的相容卡片進行無線通訊。 | 不負責專題的名單、API 或紀錄。 |
| `MFRC522` 函式庫 | 把初始化、偵測與讀取等動作包成可呼叫的函式。 | 不能把 UID 變成安全的身分證明。 |

可以把 SPI 想成兩個裝置之間的道路，`MFRC522` 函式庫像協助程式使用這條道路的翻譯員。

## 最小讀卡順序

```text
建立 RC522 物件
  → 啟用 SPI
  → 初始化 RC522
  → 等待新卡靠近
  → 確認本次讀取是否成功
  → 結束本次通訊
```

這個順序只確認硬體能否讀到練習卡，不需要顯示或保存卡片 UID。

## 常見函式的作用

| 寫法 | 常見傳入值 | 回傳或結果 | 用途 |
| --- | --- | --- | --- |
| `MFRC522 rfid(SS_PIN, RST_PIN)` | 片選與重設腳位 | 建立一個 RC522 操作物件 | 讓後續函式知道要控制哪個讀卡模組。 |
| `SPI.begin()` | 通常不需額外值 | 啟用 SPI | 準備 ESP32 與 RC522 的通訊。 |
| `rfid.PCD_Init()` | 不需額外值 | 初始化讀卡機 | 讓 RC522 進入可使用狀態。 |
| `rfid.PICC_IsNewCardPresent()` | 不需額外值 | `true` 或 `false` | 確認是否有新卡靠近。 |
| `rfid.PICC_ReadCardSerial()` | 不需額外值 | `true` 或 `false` | 確認本次卡片通訊是否成功。 |
| `rfid.PICC_HaltA()` | 不需額外值 | 結束本次卡片通訊 | 讓本次讀取有明確收尾。 |
| `rfid.PCD_StopCrypto1()` | 不需額外值 | 清理本次通訊狀態 | 避免上一筆操作狀態留到下一次。 |

`PCD` 可先理解成讀卡機本體，`PICC` 則可先理解成靠近讀卡機的卡片。這些函式回報的是偵測或通訊結果，不是授權結果。

## 在本專題的位置

```text
練習卡 → RC522 → ESP32 → HTTPS API → Gateway
```

RC522 只位於資料流的最前端。在 API 資料契約、加密信封與 Gateway 規則尚未建立前，不把真實 UID 放進網路、紀錄或畫面。

Gateway 才是套用名單與狀態規則的位置。即使 RC522 成功讀到卡片，也不代表卡片已註冊、使用者已獲允許，或系統可以控制真實設備。

## 常見誤解

### UID 可以當成安全密碼嗎？

不可以。函式庫官方說明也提醒，部分卡片的 UID 可以被複製，不能單獨作為安全身分判斷。在後續章節建立明確的資料保護與重複要求拒絕方式以前，本專題不處理真實練習卡識別資料。

### 官方 `DumpInfo` 適合直接拿來當專題程式嗎？

不適合。它會顯示 UID、卡片類型與其他資料，不符合本專題主程式的資料最小化範圍。[`DumpInfo` 練習](rc522-dumpinfo練習.md)的範圍只限專用練習卡，且不保存或傳送輸出。

### 偵測到卡片就能控制門鎖嗎？

不能。本專題只模擬狀態與燈光效果，不控制門鎖、繼電器或電磁鎖。

## 理解確認

- 能分辨 SPI、RC522 與 `MFRC522` 函式庫的角色。
- 能理解初始化、偵測、讀取與收尾的先後順序。
- 知道讀卡成功不等於身分或名單判斷成功。
- 知道後續實作不應輸出、保存或傳送真實 UID。

## 重點整理

- RC522 負責近距離卡片通訊，SPI 負責 ESP32 與 RC522 之間的資料交換。
- `MFRC522` 函式庫提供初始化、偵測、讀取與收尾函式。
- 本專題先確認受控讀卡，再由 Gateway 處理資料檢查與狀態規則。
- 卡片 UID 不是安全的身分證明，也不應出現在一般輸出與紀錄中。
