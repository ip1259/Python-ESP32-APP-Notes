# MQTT 基礎：發布、訂閱與 Broker

MQTT 是一種讓程式互相傳遞訊息的方式。你可以先把它想成「依主題分類的訊息轉送站」：一個程式送出訊息後，需要這則訊息的其他程式可以各自收到。

## 你會學到什麼

- 理解發布者、訂閱者與 Broker（訊息中介服務）的角色。
- 用 topic（主題）辨認一則訊息要送往哪一類訂閱者。
- 分辨 QoS（服務品質）三種傳遞保證，以及保留訊息的用途。
- 理解 MQTT 在本專題只分送已完成判斷的家庭情境事件。

## 開始前

- 建議先閱讀[前導技術概要](index.md)與[專題入口](../index.md)。
- 本頁是概念教材，不需要帳號、網路、Broker、ESP32 或額外套件。
- MQTT 可以傳送不同格式的訊息。本頁只看固定假資料；密碼、token（存取用的祕密字串）、完整讀卡資料和私人位址都不應放進訊息。

## 成功的樣子

讀完後，你能看懂下列例子：Gateway（集中處理資料的程式）送出一個不含個人資料的歡迎事件；燈光與顯示器都選擇接收這一類事件，所以都能各自做出反應。

```text
Gateway（發布者）
  └─ 發布到 home/events/access/welcome
                         │
                      Broker
                    ↙        ↘
          LED（訂閱者）      顯示器（訂閱者）
```

這個例子只表示訊息怎麼分送。是否通過由 Gateway 判斷；本專題也不控制實體設備。

## 認識三個角色

| 角色 | 做什麼 | 在本專題的例子 |
| --- | --- | --- |
| 發布者（publisher） | 將訊息送到一個 topic。 | Gateway 發布已完成判斷的家庭情境事件。 |
| 訂閱者（subscriber） | 表示想接收某個 topic 的訊息。 | LED、顯示器或通知服務各自接收事件。 |
| Broker（訊息中介服務） | 接收發布的訊息，轉送給符合 topic 的訂閱者。 | 只做訊息轉送，不保存名單或判斷讀卡者是否通過。 |

發布者不必知道有幾個訂閱者；訂閱者也不必直接連到發布者。這種分工適合一個事件要通知多個裝置的情境。MQTT 是採用發布／訂閱方式的訊息傳遞協定，支援一對多分送。[MQTT 5.0 標準](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)

## 用例子理解 topic

topic 用來把訊息分成不同類別，讓訂閱者只接收自己需要的訊息。觀察下列兩個 topic：

```text
home/events/access/welcome
home/events/access/denied
```

LED 若只需要歡迎效果，就訂閱 `home/events/access/welcome`；它不必處理拒絕事件。

topic 像分類路徑，不是秘密資料。實作時會為每個練習範圍選一個專屬 topic。topic 名稱不要放個人資料或內網資訊；帳密、token 與敏感訊息內容則不可公開。

## 訊息內容與路徑

閱讀下列固定假資料。第一行是 topic，第二行是 payload（訊息內容）。

```text
home/events/access/welcome
{"event_id": "evt-demo-001", "event_type": "welcome"}
```

`home/events/access/welcome` 決定分送路徑；`event_id` 和 `event_type` 是訂閱者收到後可讀取的內容。

MQTT 不限制訊息內容的格式，所以使用它的系統要先約好有哪些欄位、怎麼檢查。本頁先用固定假資料幫你分清楚「送到哪裡」和「裡面放什麼」。

## QoS 的差異

QoS 會影響訊息可能遺失或重複的情況。

| QoS | 代表意思 | 要留意什麼 |
| --- | --- | --- |
| `0` | 最多傳遞一次；網路狀況不好時可能遺失。 | 適合下一筆很快會再出現的狀態或練習事件。 |
| `1` | 至少傳遞一次；可能收到重複訊息。 | 例如同一則歡迎訊息可能出現兩次，接收程式要避免重複反應。 |
| `2` | MQTT 傳遞的這一段會送一次；做法較複雜。 | 這裡先知道：它不保證燈光或通知的效果只做一次。 |

QoS 1 的訊息可能重複，QoS 0 的訊息可能遺失。MQTT 標準也明確定義這三種保證：最多一次、至少一次、恰好一次。[MQTT 5.0 標準](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)

## 保留訊息與新事件

想像 Broker 為某個 topic 保留最後一則訊息。新的訂閱者加入時，可能先收到那一則舊訊息。

保留訊息適合表示「目前狀態」，但不適合表示每一次剛發生的讀卡或歡迎事件。若要發布一次性的效果，就不應保留它，避免新加入的裝置把舊訊息當成新事件。

## 本專題中的位置

這張圖只讓你知道 MQTT 位於哪一段；其他名稱會在對應章節逐一介紹。

```text
ESP32 ── HTTPS API ──> Gateway ── MQTT 家庭事件 ──> LED／顯示器／通知服務
                         │
                    規則與最小紀錄
```

Gateway 先處理讀卡請求、規則與紀錄；只有在結果符合條件時，才送出不含讀卡資料的家庭情境事件。

Broker 可以限制不同程式能連線或使用哪些 topic。它不判斷讀卡者是否通過，也不保存名單。

## 理解確認

- 能分辨發布者、訂閱者與 Broker 的工作。
- 能從 topic 判斷 LED 要接收哪一類事件。
- 能理解 QoS 0 的訊息可能遺失、QoS 1 的訊息可能重複。
- 知道保留訊息不是剛發生事件的可靠證明。
- 知道本專題不以 MQTT 傳送讀卡資料或決定授權。

## 常見問題

### 訂閱了 topic，就一定會收到每一則訊息嗎？

不一定。QoS、連線狀態、Broker 設定和開始訂閱的時間都會影響結果；QoS 0 本來就可能遺失。檢查時應使用固定假資料並觀察結果，不能只看一次畫面就認為系統一定可靠。

### Broker 可以幫我判斷讀卡者是否通過嗎？

不可以。Broker 的工作是依 topic 轉送訊息，並可管理 MQTT 用戶端的連線與 topic 權限；名單規則、輸入檢查與最小紀錄都應集中在 Gateway。

### 可以把每個 topic 都訂閱下來，方便除錯嗎？

不要把萬用訂閱當成預設作法。它可能收到不屬於你的訊息。除錯時只使用專屬、範圍最小的測試 topic；若不確定自己是否有權限或訊息來自哪裡，就先停止操作。

## 重點整理

- MQTT 以發布、訂閱與 Broker 分送訊息。
- topic 決定訊息類別；payload 承載內容。
- QoS 會影響遺失與重複的可能性，不能取代資料檢查。
- 保留訊息適合目前狀態，不適合當成剛發生事件。
- 在本專題中，MQTT 只分送 Gateway 已判斷完成後的家庭情境事件。
